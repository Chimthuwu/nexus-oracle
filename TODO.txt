## 1. What we’re building

**Nexus** is an immersive, fully‑3D Magic: The Gathering companion. **It is not a dashboard with 3D decoration** — no card grid, no app chrome, no traditional nav bar. The entire product is a WebGL scene, and the fixed UI (navigation rail, command bar, HUD) is designed to read as part of that scene.

- The **Oracle** is the only fixed point — a glowing, pulsating presence. You talk to it via a single floating command bar (no search bars, no dropdowns).
- Cards **do not exist** until the Oracle conjures them — they fly in from the void, arrange in front of the camera, and can be clicked to fly the camera in for a full rotate/zoom inspection.
- A minimal **navigation rail** (the “Spine”) exists for future spaces (duel arena, collection) but is collapsed, sigil‑styled, and auto‑hides during interactions — **not** a sidebar with labels.
- Two existing vanilla‑JS prototypes (`/reference/nexus-oracle.html` and `nexus-constellation.html`) define the visual language and feel — treat them as the **spec for “how it should feel”**, not as code to preserve.
- The prototype’s keyword matcher must be **replaced by the real LLM fallback chain** (§2.1) — this is the single most important functional task.

### 1.1 Navigation — “the Spine” (Track A)
- **At rest**: a thin translucent vertical line on the left edge with a few faint glowing dots — no icons, no labels, no menu appearance.
- **Icons**: sigils (✦ wordmark glyph, mana‑coloured glow dots), not generic UI icons.
- **Expand**: only on hover/focus (tap on mobile), using the same `glass` material as the command bar — never permanently open.
- **Auto‑hide**: fully fade out during card inspect mode and while the Oracle is responding; reappear (still collapsed) once the interaction settles.
- **Non‑existent destinations**: graceful “not yet” state, no dead links or console errors.

### 1.2 Space assets & visual impressiveness (Track A)
The human has a folder of space assets (`apps/web/public/assets/space/` — inventory it before writing loader code). Use them to replace/enhance the procedural background (skybox, nebula planes, star sprites). **Keep the procedural system as a fallback** for anything the asset pack doesn’t cover.

**To make it visually stunning, the final scene must include**:
- **ACES colour space** / `@react-three/postprocessing` with **bloom** and **lens flare** for the Oracle’s glow and card summoning effects.
- **Atmospheric fog** and subtle **volumetric light shafts** (using shaders or `drei`’s `SpotLight` shadows).
- **High‑quality card materials**: reflective, slightly glossy surfaces with subtle environment mapping.
- **Smooth camera easing** (cubic bezier / `lerp`) for all fly‑to‑card and orbit transitions — no jarring cuts.
- **Responsive particle systems** that react to the Oracle’s “thinking” state (pulse rate, colour shift, spark trails).

## 2. Tech stack (decided — do not relitigate)

- **Frontend**: Vite + React 18 + TypeScript + `@react-three/fiber` + `@react-three/drei` + `@react-three/postprocessing` + Tailwind CSS for DOM overlays. State: Zustand.
- **Backend**: Node 20 + TypeScript + Fastify.
- **LLM**: OpenRouter (`https://openrouter.ai/api/v1`) with **tool use** — the Oracle calls a `search_cards` tool. Provider details in §2.1.
- **Card data**: **No Scryfall.** We use a **local mock dataset** (`packages/card-data/src/mockData.ts`) initially. A free MTG API is pending confirmation — once confirmed *and verified free*, it can replace the mock **without changing the `Card` contract** (§4.1). If the MTG API never materialises or costs anything, the mock dataset remains the permanent source (a curated set of 30+ cards is enough for demo).

### 2.1 LLM provider — multi‑bucket free fallback

Every `:free` model on OpenRouter draws from **one account‑wide daily cap** — a chain of five `:free` models is not resilience. We have **two independent buckets**:

| Bucket | Provider | Keys | Notes |
|--------|----------|------|-------|
| **A** | OpenRouter | `OPENROUTER_API_KEY` | Primary: `openrouter/free` (self‑updating, filters for tool support). Optional 1–2 pinned `:free` models as same‑bucket variety. Base: `https://openrouter.ai/api/v1`. |
| **B** | NVIDIA NIM | `NVIDIA_API_KEY` … `NVIDIA_API_KEY5` | **Five keys** — rotate within this bucket before falling through to A. Base: `https://integrate.api.nvidia.com/v1`. **Must verify tool‑calling support** per model before adding to the chain. |

**General rules**:
- Never add a model you haven’t personally verified with a live call.
- Never add a model that lacks tool‑calling support.
- Keys only in `.env` — never hardcoded, never committed, never printed.
- If a chain entry starts failing, re‑verify it before assuming transient error.
- A third bucket (e.g. Groq) can be added later — not needed for the integration milestone.

**Security**: the NVIDIA keys arrived as plaintext in a `.txt` file — move them to `.env` and **delete that file**. If there’s any chance it was shared, rotate the keys.

**Pending MTG API**: if confirmed *and* genuinely free, post it in the Status Log with base URL and auth pattern. Freebuff can add it as a supplementary source without breaking the `Card` type.

4.1 Card type — canonical shape (packages/card-data/src/types.ts)

export interface Card {
  id: string;               // unique (generated for mock)
  name: string;
  manaCost: string;         // e.g. "{3}{U}{U}"
  manaValue: number;
  typeLine: string;
  oracleText: string;
  colors: string[];         // ["U"] or []
  colorIdentity: string[];
  rarity: "common" | "uncommon" | "rare" | "mythic";
  power?: string;
  toughness?: string;
  loyalty?: string;
  set: string;
  setName: string;
  artCropUrl: string;       // URL to art (can be placeholder)
  imageUrl: string;         // URL to full card image
  keywords: string[];       // ["Flying", "Trample"]
}

5. Draft Oracle system prompt (Track B)
text
You are the Nexus Oracle, an ancient intelligence woven into a Magic: The Gathering
archive. Players speak to you directly, in a floating space with no menus — you are
the interface. When you know cards that answer what they're asking, call
search_cards to summon them; don't describe cards you haven't looked up. When the
question is about rules, strategy, or anything that doesn't need specific cards,
just answer directly and call search_cards with an empty or very narrow query only if
it would genuinely help. Speak concisely — one to three sentences. Warm, a little
arcane, never corporate. You are not a search engine describing its own behavior;
you are answering a person standing in front of you.
